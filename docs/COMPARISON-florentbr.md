## 2. Регістри, яких ми не маємо

| Адреса | Назва | Призначення |
|---|---|---|
| 0x02 = 2 | GET_VIDEOTRGD | статус відео-тригера |
| 0x06 = 6 | SET_MULTI | мультиканальний режим: 0 = trigger out, 1 = pass/fail out, 2 = trigger in |
| 0x18 = 24 | SET_PHASEFINE | точне фазування (2 байти) |
| 0x32 = 50 | SET_VIDEOLINE | номер відео-рядка (для відео-тригера) |
| 0xB1 = 177 | GET_STOPPED | чи зупинений збір (для roll-режиму) |
| 0x10/0x12 = 16/18 | SET_SLOPE_THRED CH1/CH2 | верхній/нижній пороги тригера по нахилу |
| 0x26/0x2A = 38/42 | SET_TRG_HOLDOFF CH1/CH2 | holdoff, формат: мантиса 10 біт + експонента 3 біти |
| 0x32/0x3A = 50/58 | SET_TRG_CDT_EQU_H | ширина умови (FPGA ≤ V2) |
| 0x36/0x3E = 54/62 | SET_TRG_CDT_EQU_L | ширина умови (FPGA ≤ V2) |
| 0x42/0x46 = 66/70 | SET_TRG_CDT_GL | ширина умови, молодші 16 біт |
| 0x44/0x48 = 68/72 | SET_TRG_CDT_HL | ширина умови, старші біти (FPGA ≥ V3) |

Примітка: 0x32 у florentbr використовується і як SET_VIDEOLINE, і як SET_TRG_CDT_EQU_H для CH1 —
адреса контекстна, залежить від режиму тригера й версії FPGA.

## 3. Три знахідки, що змінюють нашу реалізацію

### 3.1 Поле кадру `cursor` (у нас помилково назване `slow`)

Заголовок DM-блоку за їхнім описом:

```
+0  u8   channel
+1  u32  time_sum      (для частотоміра)
+5  u32  period_num    (для частотоміра)
+9  u16  cursor        позиція тригера в кадрі, рахуючи від правого краю
+11 ...  ADC: 50 pre + 5000 семплів + 50 post
```

`cursor` — це готова апаратна точка тригера. Тобто замість нашого програмного пошуку
фронту (`Measure.displayWindow`) можна вирівнювати кадр точно за `cursor`, і тоді:
* зображення стабільне без евристики;
* CH1 і CH2 вирівнюються за одним і тим самим моментом, тобто фазова зв'язність між
  каналами зберігається (зараз ми вирівнюємо кожен канал окремо і рвемо її);
* працює і для сигналів без чіткого фронту.

Їхня формула: `offset = (SAMPLES - clip(cursor,0,SAMPLES)) - SAMPLES*trigger_position`.

### 3.2 Апаратний частотомір

```python
frequency = time_sum and period_num / time_sum * SAMPLING_RATES[-1]   # 100e6
```

Тобто `f = period_num / time_sum × 100 МГц`. Прилад сам рахує періоди по всьому кадру
(5000 семплів), це точніше за наш підрахунок фронтів у вікні, і не залежить від розгортки
так сильно. Для роботи частотоміра треба задати опорний рівень `SET_FREQREF` (0x4A/0x4B),
який ми не пишемо взагалі: `freqref = trigger_level - 5`.

### 3.3 У режимі Auto не треба опитувати TRG_D і datafinished

У них статус опитується лише для ONCE/NORMAL:

```python
if self.sweepmode:            # ONCE або NORMAL
    if not self.send(CMD.GET_DATAFINISHED) or not self.send(CMD.GET_TRIGGERED):
        continue
```

А в Auto одразу пишеться GETDATA, і якщо у відповідь прийшло 5 байтів `'E'` (EBUSY) —
пауза 60 мс і повтор. Ми ж робимо два зайвих round-trip на кожен кадр, що сповільнює цикл
і дає шанс розсинхрону. Це прямо стосується нашої проблеми «EBUSY і мерехтіння» з
роздільними розгортками.

## 4. Підтвердження наших формул (тепер з двох незалежних джерел)

| Що | florentbr | Наш код | Статус |
|---|---|---|---|
| Вертикаль | `sy = voltrange×probe / 250` → 25 кодів на поділку | `Vpp = коди × 0.04 × V/діл` | збігається |
| Діапазон АЦП | `ADC_MIN=-125, ADC_MAX=+125, ADC_RANGE=250` | `±100 кодів = ±4 поділки` на екрані | збігається (їхні ±125 = 10 поділок, ми показуємо 8) |
| Кадр | `50 pre + 5000 + 50 = 5100` | `5089` семплів у DM, центральна половина = 10 поділок | збігається |
| Частота вибірки | `prescaler = 100e6 / rate`, `rate = 100e6/prescaler` | `S = 100 МГц / SEPERATE_FREQ[tb]` | збігається |
| Roll mode | `ROLLMODE_THRESHOLD = 2500` S/s | `slowmove = 1` при tb ≥ 22 | збігається (SEPERATE_FREQ[22]=40000 → 2500 S/s) |
| Атенюатор | `ATTENUATION_THRESHOLD = 6` (vb ≥ 6) | `flag bit1 = 1 при vb > 5` | збігається |
| Zero | `zero = cal_comp - pos0×cal_ampl/100`, `pos0 = 250×offset` | `zero = Comp - pos0×Step/100`, pos0 = 0 | збігається |
| Gain | `gain = cal_gain` (clip 0..4095) | те саме | збігається |

## 5. Розбіжності та помилки в джерелі

1. **Коментар про coupling переплутаний.** У `_push_channel` написано
   `b5-6: [0:DC 1:AC 2:GND]`, але їхні ж константи `AC=0, DC=1` і наш аналіз
   декомпіляту ПК (таблиця 1,0,2 для DC,AC,GND) дають протилежне: **0 = AC, 1 = DC, 2 = GND**.
   Наш код пише 1 для DC — це правильно, помилка в їхньому коментарі.
2. **`write_flash` небезпечний.** Метод перезаписує всю флеш-партицію (2002 байти) і
   вимагає ручного виклику; перед записом робиться бекап, але за замовчуванням краще не чіпати.
   Для звичайної роботи потрібен лише `read_flash`.
3. **Порядок запису каналу інший.** Вони: ZERO_OFF → VOLT_GAIN → CHANNEL. Ми:
   CHANNEL → VOLT_GAIN → ZERO_OFF. Обидва варіанти працюють (останні команди «clear
   samples»), але їхній порядок логічніший: спершу зсув, потім підсилення, останнім канал.
4. **Формула PRE/SUF_TRG.** У них є поправка `HTP_ERR = 11`:
   `pre = 2550 - htp - 11`, `suf = 2550 + htp + 11`, де
   `htp = round(5000 × (0.5 - position))`, position 0..1.
   Ми пишемо фіксоване `half` двічі — тобто позиція тригера в нас завжди по центру і без поправки.

## 6. Практичний висновок (план на v0.4)

1. Читати `cursor` з DM-заголовка і вирівнювати кадр апаратно — це дасть стабільне
   зображення і збереже фазову зв'язність між каналами (зараз втрачену через програмний тригер).
2. Показувати частоту з апаратного частотоміра (`period_num/time_sum×100 МГц`) як основну,
   а наш підрахунок фронтів лишити запасним. Додати запис `SET_FREQREF`.
3. Прибрати опитування TRG_D/FIN в Auto-режимі, лишити лише для ONCE. На EBUSY — пауза 60 мс.
   Це має прибрати зайві round-trip і частину проблем з мерехтінням.
4. Додати тригер по спаду: біт 12 слова тригера (36), а рівень тоді пишеться як
   `(level+10, level)` замість `(level, level-10)`.
5. Додати peak-detect (SAMPLE=1) для повільних розгорток — показує викиди, які інакше
   зникають через децимацію.
6. Виправити межу малювання: зараз координати клампляться до ±100 кодів, через що
   сигнал, більший за 4 поділки, малюється пласкою лінією по краю. Треба дати йому
   виходити за межі (View обріже сам).
